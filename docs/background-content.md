# Background generation and completion mail

The web app stores generation requests in PostgreSQL (`ContentJob`). A separate worker dispatches them to BullMQ/Redis every 15 seconds. Website builds, new pages/blogs, page rewrites, new sections, and section edits all use this path. Keep both PostgreSQL and Redis persistent in production.

Each workspace may have three queued/running requests. Identical active requests reuse the existing job. The default cluster-wide limits are one website build and two content jobs. Content jobs also have a start rate of 12 per minute. These are job limits, not provider API limits: one job can make several AI calls. Set WEBSITE_JOB_CONCURRENCY, CONTENT_JOB_CONCURRENCY and CONTENT_JOBS_PER_MINUTE to tune capacity after measuring queue age, provider quotas, CPU and database connections. Multiple workers share global limits. This has not been load-tested with 1,000 simultaneous users.

Run migrations and regenerate Prisma before starting web/worker processes. Run `npm run start -w @awb/worker` under a process supervisor in production. USE_REDIS_QUEUE must be true. Submissions survive Redis downtime; the dispatcher retries delivery. Jobs retry up to three times with exponential backoff and jitter. Finished results are stored in PostgreSQL and reused if delivered again. Stalled workers use BullMQ leases. Processing is at least once; a crash during a provider call can cause a repeated provider request and charge.

Dashboard/editor notifications poll about every 15–18 seconds while visible. Page/section results wait for review; adding to the editor draft is undoable and requires Save. Rewrites reject application if the target changed meanwhile. Website builds create a new draft version; they do not publish automatically. The editor opens the generated website in a new tab to preserve current unsaved work.

Completion mail uses SES v2 in SES_MAILER_AWS_REGION, with SES_MAILER_FROM as the verified sender. Use an IAM role on AWS; dedicated SES_MAILER_ACCESS_KEY and SES_MAILER_SECRET_KEY are supported locally. Configure PUBLIC_APP_URL with the real deployed builder URL. Without it, AUTH_URL/NEXTAUTH_URL or localhost is used. Email delivery has its own outbox, lease, timeout and five attempts. Email failure never regenerates content. A crash after SES accepts mail but before the database update can produce a duplicate notification. SES delivery/bounce monitoring should be configured for production. No test email is sent by validation scripts.

Validation: web/worker/pipeline type checks, web lint, content creation/service-plan checks; `node --import tsx scripts/validate-content-worker.mts` uses one temporary local database record to verify retries, terminal failure and stored-result reuse without paid AI calls or emails.
